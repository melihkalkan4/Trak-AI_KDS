# 2. Materials and methods: system design

## 2.1. Study area, users and design requirements

TRAK-AI targets rain-fed winter wheat (*Triticum aestivum*) and oilseed sunflower (*Helianthus annuus*) production in Trakya, the European part of Türkiye, across the provinces of Edirne, Kırklareli and Tekirdağ. The retrospective modelling panel that underpins the system covers 29 districts over 2004–2025 (climate tier) and the 2017–2024 Sentinel-2 era for the vegetation and soil tiers [V; companion dataset, Kalkan and Çavdaroğlu, 2026a]. Operational development and field reconnaissance were carried out at a pilot parcel near Evrenli village (Vize, Kırklareli).

The design was governed by four requirements derived from the smallholder context of the region: (i) **offline-first operation**, because field connectivity is intermittent and cloud dependence is a single point of failure; (ii) **low unit cost**, so that the field-acquisition node is affordable at farm scale (rover bill of materials ≈ 3,440 TL [P; companion hardware paper, in preparation]); (iii) **Turkish-language, actionable advice** for non-expert users; and (iv) **honesty-aware decision logic** — the system must not present cross-validated model accuracy as if it were operational forward skill, and must fall back to transparent statistical baselines where machine learning does not demonstrably beat them (Section 2.6). Requirement (iv) is a direct consequence of the validation audit reported in the companion methods paper [V-status; Kalkan and Çavdaroğlu, 2026b, under review].

## 2.2. Edge–Fog–Cloud architecture

TRAK-AI is organised into three tiers (Fig. 2). The **edge tier** is a low-cost ground rover built around an ESP32-WROOM-32 microcontroller that acquires in-situ soil, atmospheric, positional and image data and transmits them over MQTT (Section 2.3). The **fog tier** is a laptop-class host that runs the compute-intensive models — vegetation-index forecasting, yield estimation, crop-health image classification, the retrieval-augmented advisory engine and a local large language model — together with an MQTT orchestrator and an offline SQLite store (Sections 2.5–2.11). The **cloud tier** is used only for periodic, cache-backed acquisition of Earth-observation and reanalysis inputs (Sentinel-2 via Google Earth Engine, ERA5-Land via the Copernicus Climate Data Store, and ISRIC SoilGrids; Section 2.4) and is entirely optional at run time: once inputs are cached, the fog tier operates without any network connection, and the local language model performs inference on CPU only.

The tiers communicate through a local Mosquitto MQTT broker. The rover publishes telemetry to `trakaia/rover/data`; the orchestrator publishes advisories to `trakaia/kds/advisory` and, when human-in-the-loop approval is enabled, queues processed rows on `trakaia/db/pending` for review before they are written to the database (Section 2.10) [V; src/mqtt_orchestrator.py]. This separation lets the edge node continue buffering and forwarding telemetry during connectivity gaps while the fog tier remains the single writer of record.

## 2.3. Edge tier: field rover and imaging node

The rover firmware (C++/PlatformIO for the ESP32-WROOM-32) integrates a SEN0193 capacitive soil-moisture probe (GPIO 34, ADC1), a DHT22 air temperature/humidity sensor (GPIO 4), a forward HC-SR04 ultrasonic obstacle sensor (TRIG GPIO 5, ECHO GPIO 18), a GY-NEO6MV2 (NEO-6M) GPS receiver (UART2, 9600 baud) and an AI-Thinker ESP32-CAM (UART1, 115200 baud), with an L298N dual H-bridge driving a four-wheel platform [V; src/cp3_edge/trak_ai_rover/src/config.h]. Telemetry and MQTT publication run on a 30 s cycle in the active state. Connectivity resilience is provided by a SPIFFS store-and-forward buffer, so telemetry produced during offline periods is retransmitted when the link returns; the node also supports over-the-air firmware updates and a Telnet monitor [V; src/cp3_edge/trak_ai_rover/src/main.cpp].

Two implementation details are disclosed for transparency. First, the SEN0193 unit used is a reversed-response clone (raw ADC increases with moisture), handled by an auto-detecting linear calibration (`DRY_RAW = 200`, `WET_RAW = 750`) rather than the nominal SEN0193 curve [V; config.h]. Second, and more importantly, **the ESP32-CAM performs image capture and transmission only; it does not run an on-device classifier.** The `classify_image()` routine in the camera firmware is an explicit placeholder that maps JPEG byte-size to a fixed pseudo-class and confidence, and no TensorFlow-Lite-Micro model is deployed on the device [V; src/cp3_edge/esp32_cam/src/main.cpp, lines 119–146]. All crop-health inference is therefore performed at the fog tier on the captured JPEG (Section 2.7); the "edge–fog" split for vision is capture-at-edge, infer-at-fog by design.

For transparency, the field-acquisition node is navigated and the database is seeded with demonstration coordinates near 41.045 N, 27.205 E for pilot sites EVR_01–EVR_05 [V; config.h WAYPOINTS; scripts/init_database.py INITIAL_TARLALAR]; these are explicit placeholder locations, not surveyed parcels. The single field-surveyed parcel used for the retrospective and forward-validation analyses (Sections 2.6 and 3.3) has GPS-surveyed corners with centroid 41.531 N, 27.861 E [V; companion dataset]. Throughout, the manuscript keeps the surveyed analysis parcel distinct from the demonstration pilot sites carried by the operational system, and does not present the placeholder coordinates as ground-truthed field locations.

## 2.4. Cloud tier: multi-modal ETL and data fusion

The acquisition pipeline fuses three sources into a daily master feature matrix for the pilot region over 2017–2024 [V; src/cp1_etl/main_etl_pipeline.py]: (i) Sentinel-2 L2A surface reflectance, retrieved in Google Earth Engine over a ~2 km bounding box around the pilot parcel and reduced to vegetation and water indices (NDVI, EVI, NDWI) with linear interpolation across cloud gaps; (ii) daily climate variables from **ERA5-Land** via the Copernicus Climate Data Store; and (iii) static soil properties from ISRIC SoilGrids. Each source is fetched through a hash-keyed on-disk cache, so repeated runs and offline operation reuse stored responses rather than re-hitting the APIs [V; data/cache/api/]. The three streams are left-joined on date and gap-filled to produce the modelling feature set.

The operational daily pipeline and the field-scale forward validation draw climate from **ERA5-Land** (ECMWF, via the Copernicus Climate Data Store), and apply a documented ×12.5 correction to the ERA5-Land cumulative-precipitation channel to remove an accumulation artefact [V; src/cp1_etl/mod_era5_cds.py; docs/DOKUMANTASYON.md §C.2]. The 17-feature vegetation-forecasting input inherits these ERA5-Land variables (2 m temperature statistics, precipitation, shortwave radiation, evaporation, growing-degree-days and derived indices) [V; src/cp2_model/feature_names.json]. The retrospective district-level *yield* models and the companion dataset instead draw climate from **NASA POWER (MERRA-2, NASA/GMAO)** — a pivot made for reliable district-scale access, with the two reanalyses treated as of comparable quality for agronomic variables [V; src/cp25/03_fetch_ilce_climate.py]. The two climate products are reported strictly in their own contexts — ERA5-Land for the daily operational pipeline (Sections 2.5 and 3.3) and NASA POWER for the retrospective district panel cited from the companion paper (Section 2.6) — and are never merged into a single feature set.

## 2.5. Fog tier: NDVI forecasting

Seven-day-ahead NDVI is forecast with a residual-delta formulation: the models predict the change in NDVI at horizon *t*+7 rather than its absolute level, which stabilises training against the strong seasonal signal. Four architectures are trained and compared per crop — a stacked LSTM, a convolutional LSTM (Conv1D + LSTM), a Bahdanau-style self-attention LSTM, and a gradient-boosted tree baseline (XGBoost) — all sharing a common 17-feature input over a 30-step temporal window [V; src/cp2_model/train_models_cp2.py]. The neural models use a fixed protocol (seed 42, up to 200 epochs, batch size 32, early stopping with patience 25, and learning-rate reduction on plateau with patience 10, 20 % held out for validation) and custom Keras layers registered for full save/load reproducibility [V; train_models_cp2.py]. The best architecture per crop is selected on held-out coefficient of determination and frozen for inference; the selection outcome and the full model race are reported in Section 3.1.

» Disclosure: in the deployed inference path, when no live imagery is supplied alongside a rover advisory, the forecaster falls back to the last available training window (a fixed test-mode value) rather than a live prediction [V; src/cp2_model/inference_cp2.py, "no live data — using last training window"]. This is disclosed wherever NDVI values accompany rover telemetry in Section 3.

## 2.6. Fog tier: yield estimation and honesty-aware baselines

District-scale yield (kg da⁻¹) is estimated with a layered model that adds information progressively — climate only (tier A), climate + Sentinel-2 vegetation (tier B), and climate + vegetation + soil (tier C) — with a per-crop champion selected under temporal cross-validation and calibrated with a per-province bias correction and 1.96·RMSE prediction intervals [V; src/cp25/, models/cp25/champion_metadata.json].

Crucially, the champion is selected against, and where necessary deferred to, transparent statistical baselines rather than being adopted by default. The companion methods paper established, under leave-one-year-out (temporal) versus leave-one-district-out (spatial) cross-validation on the same observations, that (a) a large, significant spatial-minus-temporal generalization gap exists for both crops, and (b) **no machine-learning configuration beats a climatology baseline for winter wheat under temporal validation**, whereas a multimodal model does add genuine skill for sunflower [V-status; Kalkan and Çavdaroğlu, 2026b, under review; these results are cited, not re-derived here]. TRAK-AI encodes this finding directly: for winter wheat the operational yield default is the climatology baseline, and machine-learning estimates are surfaced with their prediction intervals and an explicit forward-skill caveat, rather than as point forecasts implying operational accuracy. This is the concrete meaning of the honesty-aware requirement of Section 2.1. The quantitative yield-accuracy figures reported in Section 3.1 are the cross-validated district-level MAPE values from the layered pipeline; the smaller in-sample aggregate MAPE produced by an earlier eight-sample model is explicitly not used as a headline figure.

## 2.7. Fog tier: crop-health image classification

Captured field images are classified at the fog tier by a YOLOv8s-cls model into six classes — two disease classes (*downy mildew*, *rust*), two healthy classes (sunflower, wheat) and two stress classes (nutrient, drought) — each mapped to a decision-support action [V; src/image_classifier.py; model weights models/crop_health_best.pt, 10.3 MB]. When the classifier or its weights are unavailable, the pipeline falls back to a random mock label that is explicitly flagged as `mock` in the payload and tagged `[MOCK]` in the orchestrator log, so mock outputs are never silently mixed with real inference [V; image_classifier.py lines 170–184; mqtt_orchestrator.py line 482]. The overall and per-class accuracies, and an important overfitting caveat for the drought-stress class, are reported in Section 3.1.

## 2.8. Fog tier: multi-modal consensus validation

A cross-modal validator was designed to corroborate stress detections across three modalities — a satellite CNN (ResNet50), the field YOLOv8 classifier (Section 2.7), and a numerical LSTM-plus-climatology predictor — harmonised to a common four-class taxonomy and combined by a weighted-vote consensus engine [V; src/visual_validation/]. **In the shipped system this operates as a two-of-three consensus:** the satellite CNN modality is an untrained stub (no `satellite_cnn_resnet50.pt` weights are present), so the satellite arm returns unavailable and the validator degrades to the field-image and numerical modalities [V; src/visual_validation/models/satellite_cnn.py; models/visual/ empty]. This degradation is disclosed here and wherever consensus results appear; the consensus decision logic itself (agreement typing, weighted vote, flagging) is fully implemented and unit-tested [V; tests/visual_validation/].

## 2.9. Fog tier: Tri-RAG advisory and offline language model

Actionable Turkish advice is produced by a retrieval-augmented generation layer over a local corpus of ~60 agronomic documents (FAO guidance, BBCH phenology, disease and irrigation references, national extension material) [V; src/cp4_rag/]. Retrieval is hybrid: a dense index (FAISS over `intfloat/multilingual-e5-small` embeddings, top-5) and a sparse index (BM25-Okapi, top-3) are merged, de-duplicated, and re-ranked by a lightweight boost for chunks retrieved by both routes before the top-2 chunks are passed to the generator [V; src/cp4_rag/config.py, retriever.py]. » Note: this final step is a merge-and-boost heuristic, **not** a neural cross-encoder re-ranker, and is described as such. Generation uses a locally hosted Gemma-3-4B model served by Ollama (temperature 0.1, 4096-token context), so the advisory pipeline runs fully offline on CPU [V; config.py; src/cp4_rag/llm_engine.py]. » Disclosure: the current context builder injects a fixed SoilGrids soil profile into every advisory prompt rather than a per-parcel profile [V; llm_engine.py lines 360–365]. A full treatment of the retrieval design, corpus construction, latency and hallucination-resistance evaluation is reserved for a separate paper; only summary-level performance is reported here (Section 3.1, 3.4).

## 2.10. Fog tier: MQTT orchestration and human-in-the-loop approval

The orchestrator subscribes to rover telemetry, runs image classification, NDVI and yield inference, weather retrieval and an agronomic-calendar rule set, and then applies a rule-based anomaly detector (e.g. model-versus-sensor NDVI divergence, low-moisture persistence, high-confidence disease, phenology deviation, frost/heat/drought thresholds) before querying the Tri-RAG layer for advice [V; src/mqtt_orchestrator.py]. Repeated anomalies of the same type are throttled to at most one per 10 minutes to avoid alert fatigue [V; ANOMALY_THROTTLE_SEC = 600]. To keep a human in control of the data of record, an approval mode is enabled by default: processed rows are not written directly to the database but are published to `trakaia/db/pending` for review, and only approved rows are persisted [V; DASHBOARD_APPROVAL_MODE = True; DB_PENDING_TOPIC]. The broker keep-alive is set to 600 s so that long CPU-bound language-model calls do not drop the connection [V].

## 2.11. Fog tier: offline-first storage and dashboard

State is held in a single SQLite database (`data/trakai.db`, WAL mode, foreign keys enabled) whose production schema comprises field, sensor-reading, NDVI-prediction, yield-prediction and alert tables, with backward-compatibility views; the schema is authored by an idempotent bootstrapper that also seeds five demonstration pilot sites [V; scripts/init_database.py; src/database.py]. The offline-first contract is explicit: the weather, forward-validation and rover modules insert rows, the dashboards only read, and if the Earth-observation or weather services are unreachable the last cached rows still render [V; src/database.py]. » Note: an older mock-data audit document describes database-level mock seeders that no longer exist; the current database seeds only the five pilot sites (with the proxy coordinates flagged in Section 2.3) and runs no synthetic data producer [V; grep of src/database.py; docs/MOCK_DATA_AUDIT.md §3.1 is stale].

The user interface is a single-entry Streamlit application (nine tabs: overview, field detail, rover, field report, chat advisory, forward validation, cross-modal, weather, settings) that reads exclusively from the SQLite store and, on first load, triggers guarded background jobs to ensure predictions, validation artefacts and phenology are up to date [V; src/dashboard.py]. A separate Tkinter desktop application provides a live MQTT rover monitor for field runs [V; src/dashboard/dashboard.py]. Because inference, retrieval, generation and storage are all local, the complete decision-support loop — from rover telemetry to a Turkish advisory in the dashboard — executes without any external service once inputs are cached.
